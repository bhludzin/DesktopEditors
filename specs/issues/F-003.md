# F-003: Usable line width was wider than PowerPoint's

| | |
|---|---|
| Status | fixed (fixed in sdkjs 7898a3e982) |
| Severity | major |

## What differs

Even with kerning, Euro-Office fitted an extra word on lines that PowerPoint breaks.

## What PowerPoint does

Wraps as if the line were about 0.25 pt narrower than the box width minus insets (fitted to PowerPoint's own PDF export of the 838-slide deck: 93.6% -> 95.1% of lines breaking like PowerPoint; 0.15-0.45 pt all did worse).

## What Euro-Office does

Used the box width minus insets minus TEXT_RECT_ERROR (0.01 mm).

## Where to look

common/Drawings/Format/Shape.js recalculateDocContent: PRESENTATION_LINE_WIDTH_REDUCTION, presentation editor only.

## Fix idea

Done. It may be compensating for K2 (glyph advances); revisit when K2 is fixed (see K3).

## How to verify

Build and render with `python fidelity/fidelity.py loop <deck> --label <name>`, then rebuild the review facts with `python fidelity/review_prep.py <deck-dir> <name>` and look at the slides below: their findings should be gone, and no other slide should lose line-break matches or SSIM against the previous run (`fidelity.py runs <deck>`). Then set `status` and `fixed_in` in `issues.json`, add a `log` entry, and re-run `review_record.py`.

## Log

- 2026-11-21: Superseded by K3 (with K2): the fitted 0.25 pt reduction (PRESENTATION_LINE_WIDTH_REDUCTION) was compensating for the advance drift of K2. With PowerPoint's 1/576-inch advances in place, the text width is now the box width minus insets rounded down to whole 1/576-inch units. Run k2-k3-layout576: 99.6% of lines break like PowerPoint (95.1% when this fix landed).
