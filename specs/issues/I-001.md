# I-001: Fractional font sizes (sz=1275, 1313, 1875) are rounded to the nearest half point on load, so advances, line pitch and line breaks are computed for the wrong size

| | |
|---|---|
| Status | fixed (fixed in sdkjs 414ae64bd0 (fix(slide): keep fractional font sizes)) |
| Severity | major |
| Slides | 35 |
| Findings | 82 |
| Categories | font, text-glyph-spacing, text-line-spacing, text-wrap |
| Confidence in the cause | high |

## What differs

Every run whose rPr sz is not a multiple of 50 is laid out and drawn at the nearest half point. In this deck 198 runs use sz=1275 (12.75 pt, drawn at 13 pt: +1.96%), one box uses sz=1313 (13.13 pt, drawn at 13.0 pt: -1.0%, slides 396 and 403) and one placeholder uses sz=1875 (18.75 pt, drawn at 19 pt: +1.33%, slide 741). Widths and line pitch both scale by exactly the size ratio (measured 1.017-1.022 for 12.75->13, 0.990-0.993 for 13.13->13, 1.012-1.013 for 18.75->19; line pitch 17.33 vs 17.01 px, 25.33 vs 25.00 px). Lines run 7-11 px longer (or 3.5 px shorter), paragraphs rewrap and gain or lose lines, text below moves up to 5.3 px, and on 707/709 text pokes out from under frames and labels. Empty paragraphs whose endParaRPr has sz=1275 are also too tall. 35 findings on 34 slides (53, 85, 255, 396, 403, 439, 477, 478, 595, 673, 684-700, 705-709, 741, 745). The EO PDF confirms it: it uses Tf 13 where PowerPoint uses 12.72-12.75.

## What PowerPoint does

Uses the size exactly as stored, in hundredths of a point: sz=1275 is 12.75 pt, so the line pitch is 1.2 x 12.75 pt = 17.0 px at 80 px/in, and sz=1313 is 13.13 pt with a 17.52 px pitch.

## What Euro-Office does

Rounds the size to the nearest 0.5 pt when it reads the run properties: 12.75 -> 13, 13.13 -> 13, 18.75 -> 19. The rounded size is then used for advances, glyph outlines, ascent/descent and line height.

## Suspected cause

The binary reader of a:rPr/@sz does `_size = sz/100; _size = ((_size * 2) + 0.5) >> 0; _size /= 2;`. This is a leftover from Word's half-point (w:sz) model. The same reader also handles defRPr and endParaRPr, so list-style defaults and paragraph end marks are rounded too. Slide 403's reviewer thought the outlines kept 13.13 pt, but the EO PDF Tf values show that drawing is also rounded. The ink measurement there is within noise.

## Where to look

sdkjs/common/Shapes/Serialize.js: BinaryPPTYLoader.ReadRunProperties, case 17 (sz), lines 9050-9055 (`_size = ((_size * 2) + 0.5) >> 0;` at 9052)

## Fix idea

Keep hundredths of a point: `rPr.FontSize = rPr.FontSizeCS = s.GetLong() / 100;`. Then check that nothing downstream assumes half points. CTextPr compare/copy works with floats. The PPTY writer (SerializeWriter.js WriteRunProperties) must write FontSize*100 rounded to an integer, not to half points. word/Editor/Paragraph.js:13683/13753 (font size increase/decrease) round on purpose and can stay. Verify on slides 85, 396, 689 and 741: the line pitch should become 17.0 / 17.52 / 16.97 / 25.0 px.

## Also covers

Issues found separately that share this cause:

- Fractional font sizes (sz=1275, 1313, 1875) are rounded to the nearest half point on load, so lines re-break (code: common/Shapes/Serialize.js: BinaryPPTYLoader ReadRunProperties (this.ReadRunProperties = function, 8904), case 17 at lines 9049-9056.)
- Fractional font sizes (sz=1275, 1313) are rounded to half points on import, so line pitch is computed for 13 pt (code: sdkjs/common/Shapes/Serialize.js: ReadRunProperties (8904), lines 9051-9053 (case 17, font size).)
- Fractional font size sz=1313 is rounded to 13.0 pt on load, so the text is narrower and wraps differently (code: common/Shapes/Serialize.js: BinaryPPTYLoader.ReadRunProperties (8904), case 17 at 9049-9053: _size = ((_size * 2) + 0.5) >> 0; _size /= 2; (also CRunText.SetMetrics, word/Editor/Paragraph/RunContent/Text.js:211, rounds scaled sizes to half points; sizes are stored as size*64 in the item flags).)
