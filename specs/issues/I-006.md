# I-006: Theme per-script fonts (a:font script="Hebr" -> Arial) are dropped, so the Hebrew run on slide 674 falls back from Calibri: the Hebrew is garbled and the Latin text on that line switches to a fallback font

## What differs

Slide 674, Rectangle 5: the line holding a he-IL run is drawn differently in Euro-Office. ' is: ' and '“Hurry to the' are in a narrower sans fallback font, and the line ends 8 px early. The Hebrew is in a typeface other than Arial, and the he-IL hyphen is thinner. Line 2, which belongs to the same en-US run, matches within 0.25 px, so only the line that contains the RTL run is affected. Reviewers also saw the Hebrew letters garbled (logical order, wrong letters, niqqud lost), which suggests the bidi path is involved. One finding.

## What PowerPoint does

Draws the he-IL run with the theme minor font's script="Hebr" typeface (Arial; the cs typeface is empty), and draws the Latin runs on the line in Calibri (+mn-lt) like the rest of the paragraph.

## What Euro-Office does

Has no Hebr script font, because FontCollection keeps only latin/ea/cs, and cs is empty. The Hebrew falls back to a substituted system font. On that line the surrounding Latin text is drawn in a fallback font as well.

## Suspected cause

BinaryPPTYLoader.ReadFontCollection (Serialize.js 5269) skips record 3, the theme's supplemental <a:font script=...> list (5296-5300). FontCollection (Format.js 9984) holds only latin/ea/cs. The he-IL run has an empty +mn-cs, so FontScheme.checkFont (10129-10139) resolves it to +mn-lt (Calibri, which has no Hebrew glyphs) instead of the Hebr script font (Arial). The Hebrew is then shaped and drawn through glyph fallback (logical order, wrong cluster mapping, lost niqqud; the EO PDF embeds only Calibri on this page). The fallback segment apparently also captures the neighbouring Latin text on that line (' is: ', '“Hurry to the'). That spill is not yet confirmed to disappear once the Hebrew resolves to Arial.

## Where to look

sdkjs/common/Drawings/Format/Format.js: FontCollection (9984, only latin/ea/cs) and FontScheme.checkFont (10129); Latin font switch not located (candidates: common/libfont/textshaper.js CTextShaper.private_CheckNewSegment 141-193; word/Editor/Paragraph/draw/content-draw-state.js handleBidiFlow 140)

## Fix idea

Keep the supplemental <a:font script typeface> list of major/minor fonts in FontCollection (loader and PPTY record), and resolve the cs slot for runs whose lang or script is Hebrew (Hebr), Arabic (Arab) and so on to that typeface before falling back to substitution. Then trace slide 674 to find why ' is:' and '“Hurry to the' get a different font id only on the RTL line: log the grapheme font ids from HB_ShapeString and the font that handleText uses.

## Also covers

Issues found separately that share this cause:

- Hebrew run ignores the theme's Hebr script font (Arial), falls back from Calibri and comes out garbled (code: sdkjs common/Shapes/Serialize.js: ReadFontCollection (line 5269; case 3 skipped at 5296-5300); common/Drawings/Format/Format.js: FontCollection (9984) and FontScheme.checkFont (10129-10139, falls back to +mn-lt). Bidi ordering is in word/Editor/Paragraph/bidi-flow.js (BidiFlow). The glyph-fallback/shaping path was not located.)

## Log

- 2026-11-22: Fixed in the presentation editor, in four parts. (1) The theme's supplemental fonts (<a:font script typeface>) are read (BinaryPPTYLoader.ReadFontCollection record 3) and kept in FontCollection.scriptFonts. (2) A run's theme cs font (+mn-cs, +mj-cs) resolves, when the theme leaves the cs typeface empty, to the script font for the run's language: he-IL -> Hebr, ar-SA -> Arab, th -> Thai, hi -> Deva and so on (FontScheme.checkSlideCSFont, AscFormat.getComplexScriptForLanguage). x2t writes an empty theme typeface as "Arial", so a cs of "Arial" counts as empty when the theme has script fonts; a theme that really sets cs to Arial would get the script font instead (PowerPoint's themes leave cs empty). (3) In slide text, complex-script characters (Hebrew, Arabic, Syriac, Thaana, Indic, Thai, Lao, Tibetan, Khmer and their presentation forms) use the cs font, as in PowerPoint, instead of the ASCII slot Word gives Hebrew and Arabic without RTL or cs. Spaces, punctuation and other neutral characters use the cs font too in runs whose language is a complex-script one, unless a letter of another script comes before them in the run (CParagraphTextShaper.GetFontSlot, private_HandleSpace). (4) The garbled Hebrew had a second cause, independent of the font, which already existed in release 9.3.8: for right-to-left text HarfBuzz returns the glyphs in visual order, but the code points were handed out in logical order. Each glyph therefore carried another letter's code point, and the PDF is drawn from those code points (repeated shin, missing lamed, detached marks). CCodePointsCalculator now walks the clusters backwards for RTL runs (common/libfont/engine.js), and a cluster with several glyphs matches each glyph to its code point through the font's cmap (grapheme.js FillCodePointsByCmap). Test deck script-font-rules (work folder decks/script-font-rules, make_script_font_deck.py and font_per_case.py). Its theme maps Hebr to Times New Roman and Arab to Courier New, so each source is visible. he-IL Hebrew and he-IL Arabic both use the Hebr font: the language decides, not the letters. ar-SA Hebrew and ar-SA Arabic use the Arab font. en-US Hebrew uses Arial for the letters and Calibri for the spaces. he-IL Latin stays Calibri. Spaces inside a he-IL run use the Hebr font. The fonts now match PowerPoint in all 9 boxes, SSIM 0.9948. Slide 674: the Hebrew is now in Arial, in visual order and with its marks, and the Latin text on that line stays Calibri. The fallback-font spill came from the missing Hebrew font and is gone. Line breaks 18 -> 19 of 21 lines (the 2 left differ only in the extracted Hebrew text). Its SSIM fell 0.9807 -> 0.9494 because the line holding the Arial run is now taller than PowerPoint makes it (I-020), and the bet keeps no dagesh in the PDF (I-021). Harness run i004-i005-i006-c (sdkjs d3452db46b, I-004, I-005 and I-006 together) vs spacing-i002-i003-i009-c: lines 99.6% -> 99.9% (15346 -> 15388 of 15410), identical slides 774 -> 781 of 835, SSIM 0.9861 -> 0.9866. Line breaks better on 8 slides (35, 257, 396, 403, 594, 613, 674, 755) and worse on none; only 9 slides changed at all, SSIM better on 8 and worse on 1 (674, 0.9807 -> 0.9494, see I-020).
