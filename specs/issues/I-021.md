# I-021: Hebrew bet with dagesh (composed by HarfBuzz into one glyph) is drawn without the dot in Euro-Office's PDF

## What differs

Found while fixing I-006, not by the review. Slide 674: the he-IL word בַּז (bet, dagesh, patah, zayin) is drawn in Arial since I-006, but in Euro-Office's PDF the bet has no dagesh dot; PowerPoint's has it. HarfBuzz composes bet + dagesh into one glyph (Arial's U+FB31). Euro-Office's PDF maps that glyph to both code points in ToUnicode, as it should, yet the shape drawn is the plain bet. Shin + shin dot (U+FB2A) is composed the same way on this line and may lose its dot too (not checked).

## What PowerPoint does

Draws the bet with its dagesh (one glyph in its PDF, which ToUnicode maps to plain bet).

## What Euro-Office does

Draws the composed bet + dagesh glyph as plain bet.

## Suspected cause

The PDF output appears to pick each glyph from the code points stored with it (see I-006's log) rather than from the glyph id, so a composed glyph whose first code point is the plain letter is drawn as that letter. That would be in the native PDF writer (core), not in sdkjs. Not confirmed.

## Where to look

sdkjs common/libfont/grapheme.js (code points per glyph, FillCodePointsByCmap) and the PDF writer in core that turns graphemes into PDF glyphs.

## Fix idea

Trace how the PDF writer chooses the glyph for a grapheme. If it goes by the first code point, give it the glyph id. If that cannot change, a slide-only fallback is to keep the dagesh and shin dot as separate mark glyphs (no composition) for fonts whose composed forms are not reachable by code point.
