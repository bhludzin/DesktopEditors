## What differs

Found while fixing I-006, not by the review. Slide 674: the he-IL word בַּז (bet, dagesh, patah, zayin) is drawn in Arial since I-006, but in Euro-Office's PDF the bet has no dagesh dot; PowerPoint's has it. HarfBuzz composes bet + dagesh into one glyph (Arial's U+FB31). Euro-Office's PDF maps that glyph to both code points in ToUnicode, as it should, yet the shape drawn is the plain bet. Shin + shin dot (U+FB2A) is composed the same way on this line and may lose its dot too (not checked).

## What PowerPoint does

Draws the bet with its dagesh (one glyph in its PDF, which ToUnicode maps to plain bet).

## What Euro-Office does

Before the fix: drew the composed bet + dagesh glyph as plain bet, and shin + shin dot (U+FB2A, on the same line) as plain shin. The PDF holds the right glyphs; Windows' PDF renderer (Windows.Data.Pdf, which the harness rasterizes with) rejected every font embedded in it and drew the text from ToUnicode in a system font, one character per glyph.

## Suspected cause

Confirmed, and not the one first suspected: the PDF writer picks the right glyph id. core's CFontFileTrueType::WriteTTF writes each embedded subset's cmap as one format-6 subtable (platform 1, encoding 0) whose entryCount is always 256, while the subtable holds one entry per code the subset uses (its length is 10 + 2 x codes). A subset with fewer than 256 codes therefore has a cmap that claims entries past its own end. Windows rejects such a font, and its PDF renderer then draws the text from ToUnicode with a system font, one character per glyph, so a glyph that stands for several characters (bet + dagesh, shin + shin dot) is drawn as its first character alone. Euro-Office embeds one subset per font for the whole document; all 5 in the 838-slide deck's PDF (Calibri, Calibri Bold, Calibri Italic, Times New Roman, Arial: 20 to 105 codes each) were rejected. Setting only entryCount in that PDF made Windows draw the embedded fonts, the dagesh and the shin dot.

## Where to look

core PdfFile/SrcWriter/FontTTWriter.cpp: CFontFileTrueType::WriteTTF, the cmap written when pCodeToGID is given (only CFontCidTrueType passes it, FontCidTT.cpp). Harness: fidelity.py --core (render with a native core build) and core-build/build-core.ps1 outside the repo.

## Fix idea

Write entryCount as the number of codes written. Done in core; until a release carries it, the harness renders with a local core build (--core).

## How to verify

Build and render with `python fidelity/fidelity.py loop <deck> --label <name>`, then rebuild the review facts with `python fidelity/review_prep.py <deck-dir> <name>` and look at the slides below: their findings should be gone, and no other slide should lose line-break matches or SSIM against the previous run (`fidelity.py runs <deck>`). Then set `status` and `fixed_in` in `issues.json`, add a `log` entry, and re-run `review_record.py`.
