## What differs

Found while checking I-042's fix, not by the review; not a rendering difference. A copy of the 3963-slide deck (great-roll-3963) saved from the desktop app loses all 387 of its a14:imgProps picture corrections and the 234 .wdp files their a14:imgLayer elements point to; every PNG and JPEG picture is kept. The stock 9.3.8 release does the same (upstream behaviour, not a regression).

## What PowerPoint does

Writes a picture's corrections as a14:imgProps in the blip's extension list, with the original image as an a14:imgLayer (.wdp), so they can be changed or reset later; the blip itself is the corrected image.

## What Euro-Office does

Before the fix: kept the blip, the already-corrected image, so the slides should look the same after a save, but wrote no a14:imgProps and none of the .wdp files, so PowerPoint could no longer change or reset those corrections. Now a picture keeps its blip extensions (a14:imgProps with its .wdp, a14:useLocalDpi, any but svgBlip) through open, edit and save while it keeps its image: on a copy of the 3963-slide deck all 387 a14:imgProps and 234 .wdp files come back byte-identical, and PowerPoint shows the same corrections. Replacing the picture drops its extensions and their parts; Ctrl+D, a duplicated slide and copy/paste within the document keep them, and pasting into another document drops them.

## Suspected cause

Cause found: core's pptx -> editor binary conversion kept no blip extension but svgBlip (it reads a blip's extLst into PPTX::Logic::Ext, which keeps only svgBlip), so sdkjs never had the a14:imgProps or the .wdp parts to write back.

## Where to look

core OOXML/PPTXFormat/Logic/Fills/Blip.cpp/.h and BlipFill.cpp (a blip's other extensions kept as XML with their parts, and written back), Binary/Presentation/BinaryFileReaderWriter.cpp/.h (CRelsGenerator::WriteMediaPart), PPTXFormat/FileFactory.cpp, DocxFormat/FileTypes.cpp/.h and DocxFormat/Media/Image.cpp/.h (HD Photo parts as OOX::HdPhoto); sdkjs common/Drawings/Format/Format.js (CBlipFill's blipExtLst and blipExtImageId, getBlipExtLstToWrite, moveRasterImageId, the change-log serialization), common/Shapes/Serialize.js (BinaryPPTYLoader.ReadBlipExtLst, blip record 4), common/Shapes/SerializeWriter.js (WriteBlipExtLst), common/Drawings/Format/GraphicObjectBase.js and slide/Editor/Format/Slide.js (renamed images keep their extensions).

## Fix idea

Done in core and sdkjs. Writing the editor binary (presentation parts only), core keeps every a:blip/a:extLst/a:ext but svgBlip as self-contained XML and copies the .wdp and image parts it relates into the media folder, in a new blip record 4 that older readers skip: ULONG count, then per extension a record 0 with string attributes 0 uri and 1 xml, holding per part a record 0 with string attributes 0 rId, 1 relationship type and 2 media file name. Writing the pptx back, an extension is kept only if its XML parses and every rId has its part in the media folder; the parts get their original relationship type (hdphoto or image; .wdp as image/vnd.ms-photo) and renumbered rIds. Otherwise the extension is dropped, so nothing dangles. HD Photo parts load as a known media type. In sdkjs each picture fill carries the extension list with the image id it was read with and writes it back only while the fill still has that image: replacing the picture drops it, and the same image under another id (paste, upload, relink) keeps it. Copy and paste map the parts to this document's URLs; pasting into another document drops them. The desktop app saves by applying the change log to the opened binary in the converter, so the fill's change-log record carries the extension list too.

## Open questions

- The "From file" replace dialog was not driven: replacing was checked by giving a picture another of the deck's pictures through the same apply code.
- PowerPoint's COM Open accepts a dangling a14:imgLayer silently, so PowerPoint opening the saved files without a repair is a weaker check than it sounds.
- Not byte-identical in every case: attributes inside an extension are written in alphabetical order (the same XML), and the .wdp parts are named mediaN.wdp, not PowerPoint's hdphotoN.wdp.
- SmartArt and chart pictures are not covered.
- Compatibility: a bundle built before sdkjs 55d8aba01b cannot read change logs written by this one (the fill's change-log record now carries the extension list).

## How to verify

Build and render with `python fidelity/fidelity.py loop <deck> --label <name>`, then rebuild the review facts with `python fidelity/review_prep.py <deck-dir> <name>` and look at the slides below: their findings should be gone, and no other slide should lose line-break matches or SSIM against the previous run (`fidelity.py runs <deck>`). Then set `status` and `fixed_in` in `issues.json`, add a `log` entry, and re-run `review_record.py`.
