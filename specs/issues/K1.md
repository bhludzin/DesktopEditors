# K1: Filled triangle line ends are also stroked with the line pen (miter), so heads grow by ~1.6 line widths and the tip overshoots the end point

| | |
|---|---|
| Status | fixed (fixed in sdkjs 44cdab9e9f (fix(slide): draw triangle arrowheads like PowerPoint)) |
| Severity | major |
| Slides | 116 |
| Findings | 144 |
| Categories | connector-arrow |
| Confidence in the cause | high |

## What differs

144 findings on 116 slides, every one a type="triangle" tailEnd (no other line-end types or headEnds occur among the findings). Line widths and sizes: 2.25 pt med/med (40, e.g. slides 9-22, 78-105, 158-176), 3 pt med/med (23: 13 straight lines, 6 custGeom bezier freeforms, 4 prstGeom arc), 3 pt lg/lg (36, slides 118-150, 598, 632-633, 810-812), 4.5 pt med/med default w/len (43, the timeline arrow on slides 578-648, 390, 174-175), 0.75 pt med/med (2, slides 29 and 32, the thin-line minimum). All fit one model exactly: Euro-Office draws PowerPoint's correctly sized triangle, then strokes its outline with the full line pen and miter joins. The outline adds (1/cos a + tan a) x w = 1.618 w to the base width and to the length (a = 26.57 deg half-angle of a 3x3 or 5x5 head), puts the tip 1.118 w past the end point and moves the base w/2 back. Measured (coverage-weighted width profiles in the 1600-px renders, sheet px): 4.5 pt line (w=5.0 px) slide 578: PowerPoint head 14.7 wide x 14.85 long, tip at 748.1 (end 748.3); Euro-Office 22.9 x 23.1, tip 753.7 (predicted 23.1 x 23.1, tip 753.9). 3 pt lg/lg (w=3.33) slide 120: 16.5 vs 21.8-22 px, tip 3.8 px past (predicted 22.1, 3.7). 3 pt med: 9-9.6 vs 14.5-14.8 (predicted 15.4). 2.25 pt med (w=2.5): 7.4 vs 11 px, tip 2-2.8 px past (predicted 11.55, 2.8). So the size ratio is 1.55x at med and 1.3x at lg only because the constant 1.618 w excess is a smaller share of a 5 w head. Curves (custGeom, arc) are the same: head direction matches PowerPoint, only the size and overshoot differ. 0.75 pt lines: both apps apply a minimum base width (PowerPoint about 2.0 pt: head 6.7 x 6.7 px on slide 29 connector 20; Euro-Office 2.5 px at 96 dpi = 1.875 pt), and the 0.83 px outline makes Euro-Office's head 7.6 px and the tip 0.9-1.3 px past the end, i.e. 1.15x, the same mechanism at smaller magnitude.

## What PowerPoint does

Fills the line-end polygon only, no outline. Triangle head = width x length of sm 2, med 3, lg 5 times max(line width, about 2 pt) (0.7 mm, the floor LibreOffice's OOXML import also uses), tip exactly on the path end point, and the shaft is shortened under the head so a thick line's butt end never shows beside the tip (sharp tip even on 4.5 pt lines).

## What Euro-Office does

Builds the same polygon (tip on the end point, base len back, width w), fills it, then strokes the same closed polygon with the line pen; the arrow pass leaves the pen join at miter. The head grows by w/2 on every side: base width and length +1.618 w, tip 1.118 w past the end point, base w/2 further back. The shaft is stroked full length to the end point and is only hidden by the inflated head. Thin-line floor is 1.875 pt instead of about 2 pt.

## Suspected cause

DrawLineEnd's Triangle case fills (drawer.drawStrokeFillStyle) and then strokes (drawer.ds) the head polygon; the stroke uses the line's own pen width and, because CShapeDrawer.ds/drawFillStroke skip Ln.Join while IsArrowsDrawing, a miter join. The other closed line ends (Oval, Stealth, Diamond, Square, ReverseTriangle) use the same fill-then-stroke pattern, so they should be oversized the same way, although this deck has none.

## Where to look

sdkjs word/Drawing/ShapeDrawer.js: DrawLineEnd (41), case AscFormat.LineEndType.Triangle (431-483): fill at 472, second _s/_m/_l/_z + drawer.ds() stroke at 475-481 (same fill-then-stroke pattern in Diamond 113, Square 171 (232/262), Oval 266 (318/331), Stealth 335 (364/373), ReverseTriangle 378 (419/427)); CShapeDrawer.drawArrows (1623): head size from EndArrow.GetLen/GetWidth (common/Drawings/Format/Format.js 7337/7392: 2/3/5 x max(penWidth, min)), minArrowSize = 2.5 / g_dKoef_mm_to_pix mm (1.875 pt) in PDF mode (1643-1645); the shaft is stroked full length before drawArrows in CShapeDrawer.ds (2194) / drawFillStroke PDF branch (2560), path emitted by Path.prototype.drawSmart / Path2.prototype.drawSmart (common/Drawings/Format/Path.js 1627 / 3102).

## Fix idea

1) In DrawLineEnd, for Triangle (and the other filled closed ends: Stealth, Oval, Diamond, Square, ReverseTriangle) drop the second polygon + drawer.ds() and only fill (keep the PDF-editor colour fix-up for the fill). 2) Because the head is no longer inflated, the shaft's butt end would poke out beside the tip on thick lines (for med it shows within w of the tip), so shorten the stroked path at each end that has a filled line end: before stroking, move the first/last point of the first/last open subpath back along the path by about len/2 (head length converted to path units with transformScaleFactor; len/2 is always inside the head since width >= 2 x max(w, min)), while drawArrows keeps using the original end point and direction for the head. Alternatively clip the shaft stroke with the head polygon. 3) Optional, for thin lines: raise the PDF-mode floor minArrowSize from 2.5 / g_dKoef_mm_to_pix (1.875 pt) to 0.7 mm (about 1.98 pt) so 0.75 pt heads come out 6.7 px instead of 6.25 px after step 1 (residual about 0.45 px at 80 dpi otherwise). Check: slide 578 head should become 15 x 15 px with the tip at x 748.3, slide 120 16.7 x 16.7 px with the tip at y 130.0, slide 29 connector 20 about 6.7 x 6.7 px with the tip at x 269.4.

Then set `status` and `fixed_in` in `issues.json`, add a `log` entry, and re-run `review_record.py`.
